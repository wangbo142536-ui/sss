# 伙食采购模块研发确认稿

## 1. 当前状态与研发停点

本文只确认伙食采购的范围、目录、页面、数据、匹配、报价和复制策略。

- 本轮不创建伙食模块代码目录。
- 本轮不复制物料采购代码。
- 本轮不修改现有物料采购、Dashboard、基础管理和运行逻辑。
- 用户确认本文后，才开始创建伙食目录并进入全栈研发。

## 2. 真实清单分析结论

已核对船东询价文件 `NEW AMBER PROVISION QUOTATION LIST.XLSX` 和供货商报价文件 `NEW AMBER PROVISION LIST.XLSX`。

- 船东主询价页为 9 列：序号、英文名字、中文名字、备注、规格、单位、数量、单价、总价。
- 主询价页有 255 条有效明细；报价文件主表有 253 条有效明细，其中 253 条填写了单价。
- 两份主表按“中英文名 + 规格 + 单位”完全一致可直接关联 248 条。
- 询价明细中约 130 条填写规格；单位包含 `KG`、`PKT`、`DRUM`、`BTL`、`BOX`、`CASE`、`PC/PCS`、`TIN` 等。
- 供货商报价文件存在删项、新增项、无英文名项和数量调整，不能把行号或名称完全一致当作唯一匹配条件。
- 同一工作簿还包含供货商历史伙食价目表、海关库清单和辅助 Sheet；导入时不能把整个工作簿所有工作表自动合并为本次询价。

因此，伙食导入必须先识别目标工作表和表头，再做匹配预览、冲突提示和人工确认。

## 3. 与物料采购的固定差异

伙食采购复制物料采购的完整业务流程，但不复制物料的 IMPA 语义。

| 项目 | 物料采购 | 伙食采购 |
| --- | --- | --- |
| 标准编码 | IMPA/平台编码优先 | 不使用 IMPA |
| 核心匹配 | 编码优先，名称辅助 | 名称 + 规格 + 单位 |
| 候选展示 | 物料 SKU、IMPA、属性 | 伙食商品、双语名称、规格、单位、保鲜/品牌备注 |
| 价格来源 | 日价、SKU 价格、正式报价 | 本次供货商正式报价 |
| 报价入口 | 当前物料报价逻辑 | 独立供货商报价页面 |
| 批量报价 | 现有保存/导入 | 一键虚拟报价 + 导入更新 + 手工修改 |
| 比价前置 | 可存在预比价 | 必须收到有效供货商报价后比价 |

伙食页面对用户统一显示“伙食商品”或“报价项”，不展示 IMPA 编码和物料标准库状态；内部如保留 SKU 概念，也只能表示供货商自己的伙食商品记录。

## 5. 页面与角色范围

### 5.1 船代/采购方

- 伙食采购入口：上传船东清单、识别主工作表、预览和保存需求。
- 伙食询价管理：选择真实伙食供应商、发送询价、查看收件和报价进度。
- 伙食报价汇总：查看各供货商报价状态、版本、缺项和异常，不替代供货商报价操作。
- 伙食比价管理：按明细或供货商方案比价，确认采购来源。
- 伙食采购管理：生成订单并沿用物料采购的确认、备货、运输、待补给、补给中、完成流程。
- 伙食结算与评价：沿用现有结算、附件和评价口径，通过伙食业务类型隔离数据。

### 5.2 伙食供应商

- 待报价询价列表：只看到发送给当前供应商的询价。
- 报价页面：手工报价、一键虚拟报价、导出模板、导入更新、保存草稿和提交。
- 伙食订单管理：确认、拒绝、备货、发货、运输完成和履约附件。
- 伙食结算：查看当前供应商自己的结算记录和发票状态。

### 5.3 管理员

- 可查看全链路和使用“一键虚拟报价”辅助演示。
- 所有虚拟数据必须显式标记来源，不得伪装成手工或导入报价。

## 6. 完整业务流程

```text
上传船东伙食清单
  -> 识别目标 Sheet 和表头
  -> 名称/规格/单位匹配预览
  -> 人工确认异常项
  -> 保存伙食需求
  -> 选择真实伙食供应商并发送询价
  -> 供应商手工/导入/一键虚拟报价
  -> 保存草稿并提交报价
  -> 采购方查看报价完整度
  -> 进入伙食比价
  -> 选定供应商或逐项组合
  -> 生成伙食采购订单
  -> 确认/备货/运输/待补给/补给中/完成
  -> 结算/发票/付款
  -> 评价与监管复核
```

询价管理卡片保留“比价”动作，并在旁边增加“报价”入口：

- 供应商角色点击“报价”进入当前供应商报价页。
- 采购方角色点击“报价”进入报价汇总，不直接替供应商提交正式报价。
- 管理员可进入指定供应商报价页用于联调或显式虚拟报价。
- 未收到有效报价时“比价”保持禁用并显示原因；收到至少一家有效报价后开放。

## 7. 伙食清单导入规则

### 7.1 工作表识别

- 优先识别同时包含“英文名字/中文名字/规格/单位/数量”或对应英文表头的工作表。
- 一个文件出现多个候选工作表时，展示 Sheet 选择和有效行统计，不自动合并。
- 历史价目表、海关库表和辅助 Sheet 默认排除，除非用户在预览中显式选择。

### 7.2 字段映射

```text
sequenceNo       序号
nameEn           英文名字
nameZh           中文名字
remark           备注
specification    规格
unit             单位
requestedQty     需求数量
sourceUnitPrice  源文件单价，仅保留原值，不作为有效供应商报价
sourceAmount     源文件总价，仅保留原值，不作为有效供应商报价
```

- 中文名或英文名至少有一个，单位和数量必填；缺失项进入异常列表。
- 原始单元格文本和行号必须留存，便于后续追溯导入问题。
- 船东清单中的单价和总价不能自动成为某个供应商的正式报价。

## 8. 名称、规格与单位匹配规则

### 8.1 标准化

- 名称：去首尾空格、统一大小写和全半角、合并连续空格、统一常见标点；中文名和英文名分别保留。
- 规格：统一大小写、空格和乘号写法，例如 `500ML*12BTL`、`500ml x 12 btl` 归一到可比较格式。
- 单位：维护明确别名字典，例如 `KGS -> KG`、`PCS -> PC`、`PACK -> PKT`；未经确认的单位不自动换算。
- 不把 `KG` 与 `BOX`、`BTL` 与 `CASE` 等不同计价单位自动等价。

### 8.2 自动匹配等级

1. 中文名或英文名命中，且规格、单位同时一致：自动匹配。
2. 名称和单位一致，且双方规格都为空：自动匹配。
3. 名称一致但规格或单位冲突：标记“规格/单位冲突”，必须确认。
4. 仅名称近似：只提供候选，不自动匹配。
5. 同一名称、规格、单位命中多条：标记“重复候选”，必须确认。
6. 无候选：允许作为新的临时伙食商品保存，但进入待维护状态。

自动关联成功后，报价、比价和订单必须使用稳定的 `demandItemId`，不能在每次比价时重新依赖文本模糊匹配。

### 8.3 性能要求

- 一次导入批量加载候选和单位别名，建立名称/规格/单位索引。
- 禁止按“需求行数 × 供应商全部商品”逐行全量扫描。
- 模糊候选只针对未精确命中的少量行执行，并限制候选数量。

## 9. 伙食商品展示规范

所有伙食界面移除 IMPA 编码位，统一展示：

- 中文名为主标题，英文名为次标题；只有一种名称时正常占位，不显示空标签。
- 规格、单位、需求数量、供货数量分列展示。
- 备注用于品牌、鲜/冻状态、保鲜要求、包装方式和替代说明。
- 匹配状态使用“已匹配/待确认/规格冲突/单位冲突/新增商品”。
- 报价状态使用“未报价/部分报价/已报价/已提交/已更新”。
- 同一行必须能看见原需求与供应商报价差异，不以颜色作为唯一提示。

页面继续执行现有浅色海事工作台 UI：筛选区紧凑、表格横向充分利用空间、右侧不留无意义空白、状态变化有 150-250ms 轻量动效。

## 10. 供应商报价页面

### 10.1 页面结构

- 顶部上下文：询价单号、船舶、供应港、预计靠港时间、报价截止时间、币种、供应商。
- 紧凑筛选：商品名称、匹配状态、报价状态、仅看缺价、仅看数量差异。
- 主表：序号、双语名称、备注、规格、单位、需求数量、供货数量、单价、金额、来源、状态。
- 汇总区：明细数、已报价数、缺价数、数量差异数、报价合计、最后更新时间。
- 操作区：下载报价模板、导入更新报价、一键虚拟报价、保存草稿、提交报价。

### 10.2 数量规则

- `requestedQuantity` 永远保留船东原需求，不允许供应商导入覆盖。
- 供应商修改数量时保存到 `quotedQuantity`，页面明确展示差异。
- 比价默认按供应商可供数量计算；数量不足时标记“部分供货”，采购方决定拆单或改选其他供应商。

## 11. 一键虚拟报价

一键虚拟报价是显式业务工具，不是静默 Mock。

- 用户点击后先预览影响行数，再确认写入。
- 优先使用当前供应商伙食商品历史有效价或目录价。
- 无历史价时才使用稳定的演示算法生成价格；同一询价、供应商和商品重复执行应得到相同结果，避免每次刷新变化。
- 每条价格保存 `priceSource=VIRTUAL`；历史价填充保存 `priceSource=CATALOG`。
- 已手工填写或已导入的价格默认不覆盖，除非用户明确选择覆盖。
- 虚拟报价可以保存草稿和提交，但报价汇总、比价和审计记录必须显示“虚拟报价”来源。

## 12. 导入更新报价

- 系统提供当前询价的报价模板，模板携带稳定明细 ID；从平台导出的模板优先按 ID 精确更新。
- 外部船东/供应商模板没有 ID 时，按名称 + 规格 + 单位匹配并生成导入预览。
- 预览分为：可更新、数量变化、新增项、删除/缺失项、规格冲突、单位冲突、重复候选。
- 用户确认后才提交导入批次；导入失败不能留下半批数据。
- 每次提交生成报价版本，保留导入文件、操作者、时间、匹配结果和变更摘要。
- 再次导入只更新当前供应商当前询价的报价，不影响其他供应商和船东原需求。

## 13. 比价及后续流程

- 伙食比价只读取已提交且有效的供应商报价，不使用物料日价或 IMPA 候选价。
- 已匹配的报价项按 `demandItemId` 汇总；未确认冲突项不能进入自动选价。
- 比价固定为物料采购同款的两种策略：逐项最低价、单一供应商；不再提供人工组合第三策略。三家供应商报价都必须在策略区可见，单一供应商策略按用户点击的供应商生成订单。
- 同一供应商数量不足时，不得按完整需求数量计算为可成交；必须显示缺口。
- 生成订单后，确认、备货、运输、待补给、补给中、完成、附件、驳船协同、结算和评价规则与物料采购保持一致。
- 伙食数据必须带 `businessType=FOOD`，避免进入物料采购查询、统计和权限范围。

## 14. 数据隔离建议

为保证物料采购不被破坏，伙食核心数据使用独立表，公共履约能力通过 adapter 衔接。

```text

food_inquiry_supplier
food_supplier_quote
food_supplier_quote_item
food_quote_import_batch
food_quote_import_issue
food_purchase_order
food_purchase_order_supplier
```

- 不给现有 `material_demand`、`material_demand_item` 塞入伙食语义。
- 附件、驳船、结算和评价如复用现有公共表，必须增加或使用稳定的 `business_type + business_id` 关联，不复用含义不一致的 material ID。
- 新表必须建立公司、状态、询价、报价、订单和名称匹配索引；迁移脚本只能新增，不改写现有物料历史数据。

## 16. 复制与改造边界

复制的是物料采购已经验证过的业务能力和交互，不复制巨型文件结构。

## 18. 验收重点

- 真实询价文件只导入用户确认的主工作表，255 条明细可正确预览。
- 页面不出现 IMPA 编码，名称、规格、单位、需求数量和备注显示完整。
- 名称/规格/单位精确项自动匹配，冲突项不静默关联。
- 真实供应商只能看到发给自己的询价并提交自己的报价。
- 一键虚拟报价可显式填充、可追溯、重复执行稳定且不默认覆盖人工价。
- 外部报价文件可预览 248 条精确关联及剩余新增/缺失/冲突项，确认后再更新。
- 供货数量变化不覆盖船东需求数量，比价能显示数量缺口。
- 至少一家有效报价后才能比价；比价、订单、履约、结算和评价链路可继续执行。
- 伙食数据不出现在现有物料采购列表、统计和订单中。
- 新代码遵守模块目录、文件规模、CSS、权限、i18n 和构建约束。

## 19. 研发落地结果（2026-07-16）

本方案已按确认口径完成首版研发，不再处于待确认状态：

- 前端独立模块位于 `frontend/src/modules/procurement/food/`，入口页只负责页面分发；需求、询价、报价、比价、订单、结算和评价页面分别维护。
- 后端独立模块位于 `com.zswy.shipsupply.procurement.food`，按 `api/application/domain/infrastructure` 分层；数据库使用 `food_*` 独立表，不读取或写入物料采购核心表。
- 已补齐伙食采购入口、询价、报价、比价、采购、供货、结算、收款和评价菜单，以及路由、角色数据范围和中英文菜单文案。
- 报价单沿用现有物料采购布局和浅色海事工作台视觉，报价主体使用独立玻璃样式文件；通用 CSS 790 行，报价玻璃 CSS 172 行，均低于 800 行建议值或接近建议边界且低于硬上限。
- 名称、规格、单位匹配不使用 IMPA；需求数量与供应商报价数量分字段保存，数量差异在报价和比价页显式展示。

### 19.1 真实文件与接口验收

- 真实询价文件自动选择 `NEW AMBER Provision` 工作表，识别并保存 255 项，255 项进入名称/规格/单位匹配链路。
- 真实供应商报价文件匹配更新 246 项，记录 7 个导入问题；剩余 9 项由显式“一键虚拟报价”补齐并永久标记 `VIRTUAL`。
- 三家供应商均完成报价提交；逐项最低价、单一供应商两种策略均可计算，其中逐项最低价覆盖 255/255 项，单一供应商按用户选中的供应商下单。
- 已生成 1 张伙食采购订单、3 张供应商子订单和 255 条订单明细；三家供应商各推进 7 次，共完成 21 次状态迁移，主订单最终为 `SUPPLIED`。
- 三张结算单均完成 `INVOICED -> SETTLED -> PAID`，三条评价均完成提交和审核，最终为 `APPROVED`。
- 验收前后物料采购数据均为 4 张需求、4 条明细，伙食流程未改变物料数据或物料接口结果。

### 19.2 自动化与浏览器验证

- 后端伙食专项测试 18 项全部通过，覆盖名称标准化、状态机、工作表选择、三家报价/两种策略、指定单一供应商下单、应用服务、买卖双方控制器和物料隔离契约。
- 前端测试覆盖 30 个接口动作、全部订单状态按钮矩阵及报价页下载、导入、虚拟报价、保存和提交按钮。
- 前端 4 个测试文件共 11 项测试和生产构建通过；浏览器按买方与供应商真实账号检查询价、报价入口、比价、订单、供货、结算、收款和评价页面，桌面内容区按物料页面宽度铺满，390px 视口无页面级横向溢出，控制台无错误。
- 全量后端历史测试仍有 3 个既有物料测试失败，分别为乱码文案断言、控制器测试缺少现有导出服务 Mock、结算旧调用期望不一致；伙食专项测试及物料真实接口回归均通过，本次未修改物料生产逻辑以规避这些历史断言。

### 19.3 物料视觉同构整改（2026-07-16）

- 首版“沿用布局和视觉”的实现只继承了浅蓝色与玻璃背景，没有完整继承物料卡片、输入框和筛选区的结构尺寸，现已作废。
- 伙食需求录入现复用物料上传区、基础信息条、搜索筛选和匹配表格的视觉契约；五个基础字段在桌面端单行铺满，避免右侧空白。
- 伙食询价与比价复用物料 `ExpandablePanel`、`filter-toolbar`、`procurement-query-card` 完整 DOM/尺寸契约；买方与供应商询价不再叠加自定义表格。伙食订单复用 `purchase-order-query-card`、六段查询进度线和订单详情结构；后台八个真实状态映射为物料同款六个展示阶段。
- 伙食报价列表、报价详情、结算和评价统一使用物料工作台的输入框、表格、状态徽标、图标按钮和浅色玻璃表面；报价详情继续保持全宽，不使用半屏卡片布局。
- 新增 `food-material-ui.css` 作为伙食模块的物料视觉契约层，并新增结构契约测试，防止后续修改退化为“颜色相似、结构不同”。
- 比价详情复用物料 `compare-workspace`、补给信息卡、双策略板和明细表；策略固定为逐项最低价与单一供应商，展示三家供应商报价，已下单需求的确认下单按钮禁用。订单详情复用基础信息、六段执行轨、供货商执行卡、结算/明细页签；点击供货商执行卡可筛选该供货商明细。
- 结算与评价复用物料 `settlement-management-panel`、`settlement-card__content-row`、`evaluation-management-panel` 和星级结构。本轮不修改报价页面。
- 本轮前端生产构建通过，4 个测试文件共 11 个用例通过；后端伙食专项 18 项通过；内置浏览器逐页对照买方和供应商页面，1440px 桌面与 390px 移动视口均无页面级横向溢出。
