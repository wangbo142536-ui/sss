## 3. 当前代码基线与差距

### 3.1 注册和账户

- 当前注册接口先创建 `PROFILE_REQUIRED` 账户，公开注册选项只有船代和供货商。
- 后端已经识别 `BARGE_AGENT`，但自助入驻仍明确限制为船代和供货商，驳船服务商尚不能完成公开注册闭环。
- 当前供应商只使用统一 `SUPPLIER` 类型，尚未形成“物料供应 / 伙食供应”可持久化、可审核、可授权的数据契约。
- 已有企业成员、角色分配和菜单权限基础能力，可复用；本里程碑重点补齐企业自定义角色的新增/编辑/停用，以及管理员创建账户的完整闭环。

### 3.2 商品导入

- 商品管理已有 SKU、物料/伙食商品类型、导入预览、确认导入和异常处理基础能力。
- 当前能力主要围绕结构化表格和既有字段识别，距离“多种形式”仍缺少统一文件识别、Sheet/页选择、可视化字段映射、OCR 结果确认和不可识别文件的明确降级路径。
- 本目标应扩展现有商品导入能力，不再新建一套相互独立的商品库或重复导入流程。

### 3.3 报关

- 当前比价和订单已经保存 `supplyMode`、`fixedProviderType`、所选服务商、报关费和驳船预约等快照，可作为报关责任路由依据。
- 当前页面只展示报关费用，没有独立报关任务、报关状态、报关明细和默认附件下载闭环。
- 现有供应商订单详情默认按供应商子单隔离；新增“报关明细”需要在不放宽其他订单数据权限的前提下，为被指定的报关服务商单独提供采购主单的完整报关清单。

## 4. M1 - 统一注册与服务角色选择

### 4.1 用户流程

```text
创建平台账户
  -> 选择企业角色
     -> 船舶代理
     -> 供应服务商
        -> 选择物料供应能力和/或伙食供应能力
     -> 驳船服务商
  -> 填写企业资料和资质
  -> 提交审核
  -> 审核通过后生成企业管理员账户和对应默认权限
```

### 4.2 业务规则

1. 一级注册角色固定为：
   - `SHIP_AGENT`：船舶代理；
   - `SUPPLIER`：供应服务商；
   - `BARGE_AGENT`：驳船服务商。
2. 只有选择 `SUPPLIER` 时展示供应能力，能力值建议设计为可扩展集合：
   - `MATERIAL`：物料供应；
   - `FOOD`：伙食供应。
3. 建议数据模型支持同时勾选物料与伙食，前端至少选择一项；这样可避免同一企业未来扩展业务时重复注册。是否在首版 UI 限制为单选，列入审核项。
4. 注册角色决定企业基础类型和默认菜单，供应能力进一步决定物料、伙食相关菜单与业务可见范围。
5. 审核通过前只允许访问入驻资料和审核状态，不提前开放业务菜单。
6. 历史 `SUPPLIER` 企业不能被静默归类；需要管理员补充能力，或根据已有真实业务数据生成待确认建议。

### 4.3 接口与数据契约草案

- `GET /api/auth/register-options`：返回三类注册角色、供应能力选项、资质类型。
- `POST /api/auth/register`：只创建基础账户。
- `PUT /api/onboarding/company-profile`：保存 `companyType`、`supplierServiceTypes` 和企业资质。
- 企业资料建议新增 `supplier_service_types` JSON 或独立企业服务能力关联表；优先使用关联表，便于后续增加船员、金融等能力。
- 审核结果必须同步生成或绑定企业管理员角色，并按现有规则回填默认菜单权限。

### 4.4 验收标准

- 三类角色均能从注册页完成账户创建、企业资料提交、审核和登录闭环。
- 供应服务商未选择供应能力时不能提交；非供应服务商不展示也不提交供应能力。
- 物料供应商、伙食供应商登录后只获得对应业务菜单；同时具备两种能力时可看到两套菜单。
- 驳船服务商审核通过后获得驳船业务入口，不再被自助入驻白名单拒绝。
- 历史企业数据不丢失、不被错误扩权。

## 5. M2 - 企业管理员角色与账户管理

### 5.1 功能范围

- 企业注册首个审核通过的账户成为企业所有者/企业管理员。
- 企业管理员可新增、编辑、停用企业自定义角色。
- 企业管理员可为角色配置本企业可授权的菜单和按钮权限。
- 企业管理员可新增、编辑、启用/停用子账户，并为账户分配一个或多个企业角色。
- 企业管理员可重置子账户密码；子账户不能修改企业所有者身份，不能管理其他企业数据。

### 5.2 权限边界

1. 平台全局角色与企业自定义角色分离，企业管理员不得修改 `PLATFORM_ADMIN` 等全局角色。
2. 企业角色、账户、权限的所有查询和写入必须按 `companyId` 隔离。
3. 企业管理员只能授予自己企业已拥有且允许下放的权限，不能通过自定义角色越权获得平台后台能力。
4. 企业所有者角色至少保留一个有效账户，禁止停用或删除最后一个企业所有者。
5. 新增系统菜单继续遵循项目既有规则：历史企业管理员自动回填，普通子账户不自动扩权。

### 5.3 接口草案

- `GET/POST /api/company/roles`
- `PUT /api/company/roles/{roleCode}`
- `PATCH /api/company/roles/{roleCode}/status`
- `GET/PUT /api/company/roles/{roleCode}/menu-permissions`
- `GET/POST /api/company/members`
- `PUT /api/company/members/{userId}`
- `PUT /api/company/members/{userId}/roles`
- `PATCH /api/company/members/{userId}/status`
- `POST /api/company/members/{userId}/password-reset`

### 5.4 验收标准

- 新注册企业管理员能创建角色和账户，并通过新账户登录验证菜单权限生效。
- 一个账户可绑定多个角色，最终权限按并集合并，同时受企业能力上限约束。
- 停用角色不会删除历史审计记录；停用账户后令牌和后续接口访问失效。
- 跨企业查询、修改角色或账户返回无权限/不存在，不泄露目标对象信息。
- 角色名称重复、账户重复、最后一个所有者停用、越权授权都有明确错误提示。

## 6. M3 - 企业商品通用导入

### 6.1 产品目标

在企业管理的商品管理页增加统一“导入商品”入口，同一流程可导入物料和伙食商品。产品口径不承诺对任意未知文件零配置自动成功，而是做到“常见格式自动识别，复杂格式可映射确认，不支持格式明确提示并给出模板”。

### 6.2 建议支持级别

| 级别 | 文件形式 | 处理方式 | 8 月目标 |
| --- | --- | --- | --- |
| A | XLSX、XLS、CSV | 自动识别 Sheet、表头、数据区、图片和字段 | 必须完成 |
| B | PDF（文本型）、DOCX 表格 | 提取表格并进入字段映射预览 | 建议完成 |
| C | 扫描 PDF、JPG、JPEG、PNG | OCR 后进入人工确认，低置信度字段必须标红 | 条件完成 |
| D | 其他未知格式 | 拒绝直接入库，提示转换格式或下载标准模板 | 必须有清晰降级 |

### 6.3 统一导入流程

```text
选择物料/伙食商品类型
  -> 上传文件
  -> 识别文件、Sheet/页和表头
  -> 用户选择有效数据区域
  -> 自动字段映射
  -> 预览新增/更新/重复/异常
  -> 人工修正低置信度项
  -> 确认导入批次
  -> 输出成功、失败和异常明细
```

### 6.4 字段与规则

- 通用字段：商品名称、英文名称、企业 SKU、商品类型、分类、规格、单位、价格、币种、库存、品牌、产地、备注、图片。
- 物料扩展：IMPA 编码、平台编码、物料属性；继续使用现有物料名称和编码匹配能力。
- 伙食扩展：保鲜/包装说明、双语名称，不强制 IMPA 编码。
- 文件中的商品类型可作为建议，但最终以导入步骤中用户确认的类型为准；禁止把伙食商品误写为物料。
- 每次导入生成批次、原文件、来源行/页、字段映射、置信度、操作者、时间、确认结果和异常记录。
- 确认导入必须事务化；重复执行同一批次不得产生重复商品。

### 6.5 验收标准

- 至少用物料 XLSX、伙食 XLSX、CSV、文本 PDF、扫描图片各一份真实样本验证。
- 多 Sheet 文件不会自动合并历史价目表或辅助表，必须由用户确认目标数据区。
- 预览能准确区分新增、更新、重复、冲突和不可识别项；未确认前不写正式商品表。
- 一批部分异常时，用户可只确认有效行；异常可导出并在修正后重新提交。
- 商品类型、企业隔离、SKU 唯一性、图片持久化和导入审计均通过接口与浏览器验证。

## 7. M4 - 采购订单一键报关

### 7.1 核心互斥规则

报关入口由比价单最终保存并随订单快照固化的履约方式决定，两个入口互斥，不能同时出现，也不能相互改变状态。

| 订单快照 | 报关责任方 | 展示位置 | 另一端处理 |
| --- | --- | --- | --- |
| `supplyMode=SEA` 或 `fixedProviderType=BARGE` | 被选中的驳船服务商 | 驳船服务的预约船舶详情 | 所有供应商订单均不展示“报关明细” |
| `supplyMode=LAND` 或 `fixedProviderType=SUPPLIER` | 被选中的供应服务商 | 船供管理 - 供应商的订单详情 | 驳船预约不展示该订单报关入口 |

补充规则：

1. 责任路由只读取下单时的快照，不根据页面当前筛选或后续临时修改猜测。
2. 同一采购主单只生成一个当前有效的报关任务。
3. 供应商模式下，只有被选为报关责任方的供应服务商能看到“报关明细”；其他参与供货的供应商仍只能看到自己的订单明细，且不显示报关页签。
4. 驳船模式下，即使采购主单包含多个供应商子单，供应商端也完全不展示该单的报关明细。
5. 既有订单若缺少履约快照，默认不生成报关入口，避免错误授权；是否批量回填列入审核项。
6. 报关费只读取订单/预约已经固化的 `fixedCustomsFee` 或 `customsFee` 快照；新增报关任务只记录引用值，不再次计费、不改写订单总额，也不重复生成结算费用。
7. 页面隐藏只负责交互，不能作为权限控制；所有报关查询、明细、状态写入和附件下载都必须由后端校验登录企业是否为采购方、指定报关责任方或平台管理员。

### 7.2 驳船端页面

- 在截图一红框对应的“预约船舶”区域增加“一键报关”按钮。
- 在预约船舶详情的“报关费”下增加“报关状态”。
- 默认显示 `--`；点击“一键报关”成功后显示“已报关”。
- 已报关后按钮禁用或改为“已报关”，同时显示“下载附件一”。
- 多个预约船舶页签共用采购主单报关任务，不因切换页签重复报关。

### 7.3 供应商端页面

- 在截图二“订单明细”右侧增加“报关明细”页签。
- 只有供应商履约模式且当前登录企业是被指定报关责任方时展示该页签。
- 报关明细展示采购主单全部报关所需商品数据，包含所有供应商子单的数据，而不是只显示当前供应商自己的供货明细。
- 全量数据权限只开放给“报关明细”专用接口和专用页面，不改变现有订单明细、金额、结算和附件的供应商隔离规则。
- 页签内展示报关状态、一键报关和附件下载；默认 `--`，成功后显示“已报关”。

### 7.4 报关明细建议字段

- 采购单号、询价/比价单号、船名、IMO、补给港、预计到港/送达时间。
- 商品序号、业务类型（物料/伙食）、商品名称、英文名称、IMPA/企业 SKU（适用时）、规格、数量、单位、单价、金额、币种、供货企业。
- 履约方式、报关责任类型、责任企业、报关费、报关状态、报关人、报关时间。
- 默认附件名称、附件版本、下载时间；下载行为写审计日志。

### 7.5 状态与幂等

首版只引入两个业务状态：

```text
UNDECLARED  -> 页面显示“--”
DECLARED    -> 页面显示“已报关”
```

- 一键报关从 `UNDECLARED` 原子更新为 `DECLARED`，同时记录操作者和时间。
- 重复点击必须幂等，不能生成多条任务或多份重复附件。
- 首版不伪造海关回执，不增加“海关已受理/审核通过”等外部系统状态；外部接口接通后另行扩展状态机。

### 7.6 数据与接口草案

建议新增独立海关业务模块，遵循 `frontend/src/modules/customs/` 和后端 `customs/api/application/domain/infrastructure` 分层，不继续向 `WorkbenchPage.vue` 堆积大段新状态和页面逻辑。

现有物料采购和驳船页面仍位于旧工作台时，通过 `legacy-adapters` 接入同一个报关 service；禁止在 `WorkbenchPage.vue`、新海关模块和伙食模块分别维护三套状态或重复提交逻辑。

建议核心数据：

- `customs_declaration`：采购主单、业务类型、责任方类型/企业、履约快照、状态、报关费、操作者、时间、默认附件版本。
- `customs_declaration_item_snapshot`：报关时固化采购主单全部明细，保存来源供应商子单但不按子单裁剪。
- `customs_declaration_attachment`：附件名称、文件标识、版本、来源、上传/创建时间。

建议接口：

- `GET /api/customs/declarations/by-purchase-order/{purchaseOrderId}`
- `POST /api/customs/declarations/{declarationId}/declare`
- `GET /api/customs/declarations/{declarationId}/items`
- `GET /api/customs/declarations/{declarationId}/attachments/default/download`
- 驳船预约和供应商订单详情接口只返回 `customsDeclarationAvailable`、状态和任务 ID，不直接复制整份报关数据。

### 7.7 默认“附件一”

- 默认附件使用用户提供的《凯珀物资上船通知单.pdf》。已核对文件共 57 页，包含物资上船通知单、海关监管单、商品清单和船舶搭靠外轮许可证。
- 该文件包含企业、联系人和采购业务信息，不放在无需登录即可访问的前端 `public` 目录，也不在本次规划阶段复制进代码仓库。
- 外部海关接口暂未接通期间，由平台内部受权限控制的下载接口返回固定“附件一”；点击即可下载，不伪造外部报关结果。
- 只有报关责任方、采购方授权人员和平台管理员可下载；其他供应商、其他驳船企业和匿名用户不可访问。
- 后续接通真实海关接口时，默认附件保留为演示/历史模板，真实回执以新附件类型和来源标记保存，不能静默覆盖。

### 7.8 验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| 比价选择驳船并生成订单 | 选中驳船可在预约船舶位置报关；全部供应商端无报关页签 |
| 比价选择供应服务商并生成订单 | 被选供应服务商看到报关页签；驳船端无报关入口 |
| 一个采购单包含多个供应商子单 | 报关责任供应商在报关页看到全部采购明细；普通订单明细仍只看自己的 |
| 未报关 | 状态显示 `--`，无“已报关”误导 |
| 首次一键报关 | 状态原子变为“已报关”，记录操作者和时间，附件一可下载 |
| 重复点击报关 | 返回同一结果，不新增重复记录 |
| 越权访问报关明细或附件 | 返回无权限/不存在，不泄露订单是否存在 |
| 物料与伙食订单 | 使用同一报关领域契约，以 `businessType` 隔离并正确展示各自字段 |

## 8. 建议研发顺序与依赖

### 第 1 周：契约和注册基础

- 冻结三类注册角色、供应能力模型和历史供应商迁移策略。
- 完成注册选项、企业资料、审核与默认权限契约。
- 完成企业角色/账户接口契约和越权矩阵。

### 第 2 周：管理员能力与商品导入

- 完成企业角色、账户、菜单权限和密码重置闭环。
- 在现有商品导入基础上完成 XLSX/XLS/CSV 统一入口、字段映射和批次确认。
- 评估并接入 PDF/DOCX/OCR 识别，无法稳定识别的格式走人工确认与降级提示。

### 第 3 周：报关领域与双端页面

- 固化比价到订单的报关责任路由快照。
- 完成报关任务、全量明细快照、状态幂等和附件权限。
- 完成驳船预约入口、报关状态，以及供应商订单“报关明细”页签。

### 第 4 周：联调、回归和验收

- 使用船代、物料供应商、伙食供应商、驳船服务商、企业管理员、普通子账户执行角色矩阵验证。
- 使用 SEA/BARGE 与 LAND/SUPPLIER 两条真实订单链路验证报关互斥。
- 验证物料/伙食多格式商品导入、异常回滚、重复批次和跨企业隔离。
- 完成前后端构建、专项测试、真实接口验证和内置浏览器逐页对照；涉及后端时按项目规则先停旧 `8080` 服务再启动新服务。

## 9. 研发完成后的统一回传要求

全栈研发线程必须一次性回传：

- 改动范围和关键文件；
- 数据库迁移、接口和字段变化；
- 注册/角色/账户权限矩阵；
- 商品导入支持格式和识别限制；
- 报关责任路由、状态、附件与越权验证结果；
- 前后端构建、自动化测试、真实接口和浏览器自测结果；
- 是否需要重启、历史数据是否需要回填、剩余风险。

## 10. 审核前待确认项

1. 供应服务商能力首版 UI 是单选“物料或伙食”，还是允许同时勾选两种能力？建议数据层支持多选，UI 也允许多选。
2. 供应商报关明细的“采购订单全部数据”是否按本文件字段清单执行，还是还要包含采购方内部利润、结算等敏感字段？建议只开放海关申报必需数据，不开放利润和结算。
3. 历史订单是否生成报关任务？建议首版只覆盖审核通过后新生成且履约快照完整的订单，历史订单后续按明确规则补录。
4. 默认附件一是否允许进入受权限控制的后端文件存储并随部署发布？如不允许，需要提供受控对象存储位置或由管理员首次上传。

以上四项确认后再进入研发。
