## 3. 研发前代码基线与差距

### 3.1 注册和账户

- 当前注册接口先创建 `PROFILE_REQUIRED` 账户，公开注册选项只有船代和供货商。
- 后端已经识别 `BARGE_AGENT`，但自助入驻仍明确限制为船代和供货商，驳船服务商尚不能完成公开注册闭环。
- 当前供应商只使用统一 `SUPPLIER` 类型，尚未形成“物料供应 / 伙食供应”可持久化、可审核、可授权的数据契约。
- 已有企业成员、角色分配和菜单权限基础能力，可复用；本里程碑重点补齐企业自定义角色的新增/编辑/停用，以及管理员创建账户的完整闭环。
- 平台权限接口已经能读取所有企业账户、所属企业、状态和角色，但当前缺少企业管理员/内部账户来源标识、企业分组视图，以及平台侧启用/停用账户的闭环。

### 3.2 商品导入

- 商品管理已有 SKU、物料/伙食商品类型、导入预览、确认导入和异常处理基础能力。
- 当前导入接口没有接收批次商品类型，后端预览会把所有导入行固定为 `MATERIAL`；前端虽可逐行改成 `FOOD`，但此前已经执行了物料名称与 IMPA 匹配。企业同时经营物料和伙食时确实会出现误分类和错误匹配风险。
- 当前企业 SKU 唯一键未包含商品类型，同一企业的物料和伙食若使用相同 SKU 编码会互相冲突；所有按 SKU 查询、更新和判重也尚未强制携带 `productType`。
- 当前文件选择控件虽允许选择 XLSX、XLS、CSV，但后端仍按 XLSX 压缩包和工作表结构解析，现阶段只有 XLSX 能作为稳定基线；本里程碑收敛为固定双 Sheet XLSX 模板，其他格式只提供转换提示和模板下载。
- 当前导入流程没有固定“物料”“伙食”Sheet 契约；本次直接用 Sheet 名隔离商品类型，避免继续增加逐行类型识别和复杂文件推断。
- 本目标应扩展现有商品导入能力，不再新建一套相互独立的商品库或重复导入流程。

### 3.3 报关

- 当前比价和订单已经保存 `supplyMode`、`fixedProviderType`、所选服务商、报关费和驳船预约等快照，可作为报关责任路由依据。
- 当前页面只展示报关费用，没有独立报关状态、报关明细、海关服务查询记录和默认附件下载闭环。
- 现有“海关服务”只有占位页；本里程碑新增“报关管理”，由驳船端或供应商端的一键报关动作向该查询页插入演示记录。

## 4. M1 - 统一注册与服务角色选择

### 4.1 用户流程

```text
在统一注册页选择企业角色
     -> 船舶代理
     -> 供应服务商
        -> 选择物料供应能力和/或伙食供应能力
     -> 驳船服务商
  -> 填写账号、密码和确认密码
  -> 填写企业资料并选择资质文件
  -> 一次提交注册与审核资料
  -> 审核通过后生成企业管理员账户和对应默认权限
```

### 4.2 业务规则

1. 一级注册角色固定为：
   - `SHIP_AGENT`：船舶代理；
   - `SUPPLIER`：供应服务商；
   - `BARGE_AGENT`：驳船服务商。
2. 只有选择 `SUPPLIER` 时展示供应能力，能力值建议设计为可扩展集合：
   - `MATERIAL`：物料供应；
   - `FOOD`：伙食供应。
3. 建议数据模型支持同时勾选物料与伙食，前端至少选择一项；这样可避免同一企业未来扩展业务时重复注册。是否在首版 UI 限制为单选，列入审核项。
4. 注册角色决定企业基础类型和默认菜单，供应能力进一步决定物料、伙食相关菜单与业务可见范围。
5. 审核通过前只允许访问入驻资料和审核状态，不提前开放业务菜单。
6. 历史 `SUPPLIER` 企业不能被静默归类；需要管理员补充能力，或根据已有真实业务数据生成待确认建议。
7. 新用户不得再经历“先创建基础账号、再跳转企业入驻页”的两步流程；公开注册页必须在同一表单中收齐账号、角色、企业资料和资质，并以一次提交进入待审核状态。
8. 历史 `PROFILE_REQUIRED` 账户及审核驳回账户继续使用原企业资料页补交或重提，兼容入口不作为新用户注册的第二步骤。

### 4.3 接口与数据契约草案

- `GET /api/auth/register/options`：返回三类注册角色、供应能力选项、资质类型。
- `POST /api/auth/register-and-submit`：以 multipart 一次提交账号、密码、企业角色、供应能力、企业资料和资质文件；账号、企业、资质关联和待审核状态在同一事务中完成。
- `POST /api/auth/register` 与 `POST /api/onboarding/company-profile`：仅保留给历史兼容和未完成/驳回资料补交，不再作为新用户的公开注册主流程。
- 企业资料建议新增 `supplier_service_types` JSON 或独立企业服务能力关联表；优先使用关联表，便于后续增加船员、金融等能力。
- 审核结果必须同步生成或绑定企业管理员角色，并按现有规则回填默认菜单权限。

### 4.4 验收标准

- 三类角色均能从注册页完成账户创建、企业资料提交、审核和登录闭环。
- 公开注册只展示一个完整表单和一个“提交审核”主操作；提交成功直接进入审核状态，不再跳转到第二个企业入驻步骤。
- 注册提交任一字段、资质文件或数据库操作失败时不得留下 `PROFILE_REQUIRED` 半成品账号、孤立企业或孤立资质记录。
- 供应服务商未选择供应能力时不能提交；非供应服务商不展示也不提交供应能力。
- 物料供应商、伙食供应商登录后只获得对应业务菜单；同时具备两种能力时可看到两套菜单。
- 驳船服务商审核通过后获得驳船业务入口，不再被自助入驻白名单拒绝。
- 历史企业数据不丢失、不被错误扩权。

## 5. M2 - 企业管理员与平台账户监管

### 5.1 功能范围

- 企业注册首个审核通过的账户成为企业所有者/企业管理员。
- 企业管理员可新增、编辑、停用企业自定义角色。
- 企业管理员可为角色配置本企业可授权的菜单和按钮权限。
- 企业管理员可新增、编辑、启用/停用子账户，并为账户分配一个或多个企业角色。
- 企业管理员可重置子账户密码；子账户不能修改企业所有者身份，不能管理其他企业数据。

### 5.2 平台级账户监管

- 只有 `PLATFORM_ADMIN` 或后续等价的“平台账户管理”权限可以进入平台账户监管页；这里的“平台用户”不包含普通船代、供应商、驳船服务商或企业子账户。
- 平台管理员可以查看所有已注册企业，以及每家企业的注册管理员账户和企业内部新增账户。
- 页面以企业为一级分组，企业行展示企业名称、企业类型、供应能力、企业状态、账户总数和启用账户数；展开后展示该企业全部账户。
- 账户行至少展示账号、姓名、手机号、账户来源、管理员标识、角色、账户状态、创建时间和最后登录时间；账户来源固定区分“注册管理员”和“企业内部创建”。
- 当前前端“企业账户列表”仍是静态预览，不能作为已完成功能；正式页面必须绑定真实全量查询、分页和筛选结果，企业与账户数量均以后端数据为准。
- 平台管理员可启用或停用单个账户。停用必须填写原因并二次确认，成功后立即使该账户已有登录令牌失效；重新启用不自动修改原角色和菜单权限。
- 平台管理员可以停用企业注册所有者、企业管理员和普通内部账户，但不能通过本功能操作平台管理员账号；企业所有者被停用只影响该账号，不联动停用企业。二次确认必须清楚展示目标企业、账号和账户类型。
- 账户启停与企业启停是两套动作。停用一个企业管理员账户不等于停用整家企业，也不影响该企业其他有效账户；企业整体停用需走独立企业状态操作，不能复用账户按钮。
- 禁止平台管理员停用自己，禁止停用最后一个有效平台管理员；所有启停动作记录操作人、原因、时间、目标企业和目标账户。

### 5.3 权限边界

1. 平台全局角色与企业自定义角色分离，企业管理员不得修改 `PLATFORM_ADMIN` 等全局角色。
2. 企业角色、账户、权限的所有查询和写入必须按 `companyId` 隔离。
3. 企业管理员只能授予自己企业已拥有且允许下放的权限，不能通过自定义角色越权获得平台后台能力。
4. 企业侧自主管理时，企业所有者角色至少保留一个有效账户，禁止企业管理员停用或删除最后一个企业所有者；平台级监管按 5.2 的独立权限、强确认和审计规则执行。
5. 新增系统菜单继续遵循项目既有规则：历史企业管理员自动回填，普通子账户不自动扩权。
6. 平台账户列表可以跨企业读取，但企业管理员仍只能读取和管理本企业账户；不能因为平台页面新增跨企业接口而放宽企业端接口。
7. 平台账户页面不展示密码、密码哈希、令牌或其他认证秘密。

### 5.4 接口草案

- `GET/POST /api/company/roles`
- `PUT /api/company/roles/{roleCode}`
- `PATCH /api/company/roles/{roleCode}/status`
- `GET/PUT /api/company/roles/{roleCode}/menu-permissions`
- `GET/POST /api/company/members`
- `PUT /api/company/members/{userId}`
- `PUT /api/company/members/{userId}/roles`
- `PATCH /api/company/members/{userId}/status`
- `POST /api/company/members/{userId}/password-reset`
- `GET /api/platform/companies/accounts`：按企业分组查询全部注册管理员和内部账户，支持企业类型、供应能力、账户来源、角色、状态、关键词、页码和每页数量筛选。
- `PATCH /api/platform/accounts/{userId}/status`：平台管理员启用/停用账户，提交 `status` 和必填 `reason`。
- 现有 `GET /api/admin/users` 可作为数据基础，但正式研发时应补齐 `companyId`、企业类型、供应能力、账户来源、管理员标识、创建时间、最后登录时间、分页和筛选能力，避免前端猜测；不复用“注册审核列表”的页面语义。

### 5.5 验收标准

- 新注册企业管理员能创建角色和账户，并通过新账户登录验证菜单权限生效。
- 一个账户可绑定多个角色，最终权限按并集合并，同时受企业能力上限约束。
- 停用角色不会删除历史审计记录；停用账户后令牌和后续接口访问失效。
- 跨企业查询、修改角色或账户返回无权限/不存在，不泄露目标对象信息。
- 角色名称重复、账户重复、最后一个所有者停用、越权授权都有明确错误提示。
- 平台管理员能按企业展开查看注册管理员和内部账户，并能筛选、启用和停用目标账户。
- 平台停用账户后，该账户已有会话立即失效，其他同企业账户不受影响；重新启用后原角色和菜单权限保持不变。
- 普通平台业务用户、企业管理员和企业子账户不能调用跨企业账户列表或平台启停接口。
- 平台管理员不能停用自己或最后一个有效平台管理员，失败原因清晰且写入安全日志。

## 6. M3 - 企业商品双 Sheet 导入

### 6.1 产品目标

在企业管理的商品管理页增加统一“导入商品”入口，并提供一个固定 XLSX 模板。模板包含“物料”和“伙食”两个 Sheet，商品类型直接由所在 Sheet 决定，不再让企业选择导入模式，也不要求在每行重复填写商品类型。

同一企业可以同时经营物料和伙食：物料只能填写在“物料”Sheet，伙食只能填写在“伙食”Sheet。一个文件可以同时导入两个 Sheet，也可以只填写其中一个；系统不得根据当前列表筛选器、历史选择或 IMPA 匹配结果改变 Sheet 对应的商品类型。

### 6.2 建议支持级别

| 级别 | 文件形式 | 处理方式 | 8 月目标 |
| --- | --- | --- | --- |
| A | 平台标准 XLSX 模板 | 固定读取“物料”和“伙食”两个 Sheet，按 Sheet 分别校验和导入 | 必须完成 |
| B | 外部 XLSX | 必须复制到标准模板，或同时满足固定 Sheet 名和对应表头后才能进入预览 | 建议完成 |
| C | XLS、CSV、PDF、DOCX、图片 | 首版不直接入库，提示转换或下载标准模板 | 明确降级 |
| D | 其他未知格式 | 拒绝直接入库并给出模板下载入口 | 必须完成 |

### 6.3 统一导入流程

```text
下载或打开双 Sheet 标准模板
  -> 在“物料”Sheet 填写物料
  -> 在“伙食”Sheet 填写伙食
  -> 上传 XLSX 文件
  -> 分别读取两个固定 Sheet 和表头
  -> 分 Sheet 预览新增/更新/重复/异常
  -> 人工修正异常项
  -> 确认导入
  -> 输出成功、失败和异常明细
```

### 6.4 双 Sheet 隔离规则

1. 模板 Sheet 名固定为“物料”和“伙食”，顺序也固定；首版不提供“混合 Sheet”和逐行商品类型选择。
2. “物料”Sheet 中的有效行统一写入 `MATERIAL`；“伙食”Sheet 中的有效行统一写入 `FOOD`。
3. 两个 Sheet 使用各自表头模板。物料保留 IMPA、平台编码等字段；伙食保留保鲜、包装、规格、单位等字段，不强制 IMPA。
4. 上传后预览区固定分成“物料”和“伙食”两个页签，页签显示有效数、异常数；空 Sheet 显示“本次无数据”，不作为错误。
5. 物料只进入物料名称、IMPA 和平台编码匹配；伙食只进入伙食名称、规格、单位匹配，禁止伙食进入 IMPA 推荐。
6. 如果缺少固定 Sheet、Sheet 名被修改或表头不匹配，阻止确认并提示下载标准模板，不能猜测它属于物料还是伙食。
7. 确认时按 Sheet 分别提交并返回结果；一个 Sheet 失败不能把另一个 Sheet 标记成功。
8. SKU 判重和更新使用 `companyId + productType + supplierSkuCode`；同一企业同一类型不能重复，同一编码可以分别存在于物料和伙食中。

### 6.5 字段与规则

- 通用字段：商品名称、英文名称、企业 SKU、商品类型、分类、规格、单位、价格、币种、库存、品牌、产地、备注、图片；其中商品类型是系统字段，由 Sheet 自动写入，不出现在模板逐行表头中。
- 物料扩展：IMPA 编码、平台编码、物料属性；继续使用现有物料名称和编码匹配能力。
- 伙食扩展：保鲜/包装说明、双语名称，不强制 IMPA 编码。
- 商品类型由固定 Sheet 决定，预览页面只允许修正商品内容，不允许把单行从“物料”改成“伙食”或反向改型；需要改型时必须回到模板移动到正确 Sheet 后重新上传。
- 每次导入记录原文件、Sheet 名、来源行、操作者、时间、确认结果和异常记录。
- 确认导入以单个 Sheet 为事务边界；物料 Sheet 与伙食 Sheet 分别提交、分别返回结果。重复执行同一文件批次不得产生重复商品。

### 6.6 采购取数与比价隔离

- 物料比价候选继续从 `shop_sku` 获取，只允许 `product_type=MATERIAL` 且已上架的商品进入物料候选池；现有物料候选查询已经具备该过滤，不得删除或放宽。
- 伙食商品在供应商选品、报价预填或商品匹配阶段从同一 `shop_sku` 商品库获取时，必须固定过滤 `product_type=FOOD`，不能依赖前端当前页签过滤后再全量返回。
- 伙食最终生成比价仍读取已经提交并匹配成功的 `food_supplier_quote_item`，该表本身属于伙食报价，不需要在最终比价查询中再次连接商品表临时过滤。
- 物料接口的业务上下文固定为 `MATERIAL`，伙食接口的商品库取数上下文固定为 `FOOD`；后端不能接受调用方把两类上下文任意互换。
- 商品列表公共查询仍可使用 `productType` 参数，但物料比价和伙食选品等专用接口必须在服务端固定类型，避免漏传参数造成串库。

### 6.7 验收标准

- 使用一份同时包含物料和伙食的标准 XLSX、一份仅物料有数据的标准 XLSX、一份仅伙食有数据的标准 XLSX 验证。
- 除固定“物料”“伙食”外的其他 Sheet 不参与导入，也不能自动合并历史价目表或辅助表。
- 预览能准确区分新增、更新、重复、冲突和不可识别项；未确认前不写正式商品表。
- 一批部分异常时，用户可只确认有效行；异常可导出并在修正后重新提交。
- 商品类型、企业隔离、SKU 唯一性、图片持久化和导入审计均通过接口与浏览器验证。
- 同一企业可在一个文件中同时导入两个 Sheet，预览和结果按 Sheet 清楚分开。
- 缺少固定 Sheet、修改 Sheet 名、表头错误或把数据放错 Sheet 时有明确提示，系统不自动猜测类型。
- 伙食商品不会生成 IMPA 推荐，物料和伙食使用相同企业 SKU 编码时不会互相覆盖。
- 导入确认后按物料、伙食分别返回成功数、失败数和异常数，能够从正式列表按类型准确查到对应商品。
- 物料比价候选只包含 `MATERIAL`，即使伙食商品名称或 SKU 相同也不会进入物料比价。
- 伙食选品、报价预填和商品匹配只返回 `FOOD`；最终伙食比价只使用已提交的伙食报价，不混入物料候选或物料价格。

## 7. M4 - 采购订单一键报关

### 7.1 核心互斥规则

报关入口由比价单最终保存并随订单快照固化的履约方式决定，两个入口互斥，不能同时出现，也不能相互改变状态。

| 订单快照 | 报关责任方 | 展示位置 | 另一端处理 |
| --- | --- | --- | --- |
| `supplyMode=SEA` 或 `fixedProviderType=BARGE` | 被选中的驳船服务商 | 驳船服务的预约船舶详情 | 所有供应商订单均不展示“报关明细” |
| `supplyMode=LAND` 或 `fixedProviderType=SUPPLIER` | 被选中的供应服务商 | 船供管理 - 供应商的订单详情 | 驳船预约不展示该订单报关入口 |

补充规则：

1. 责任路由只读取下单时的快照，不根据页面当前筛选或后续临时修改猜测。
2. 同一采购主单只生成一条报关管理记录。
3. 供应商模式下，只有被选为报关责任方的供应服务商能看到“报关明细”；其他参与供货的供应商仍只能看到自己的订单明细，且不显示报关页签。
4. 驳船模式下，即使采购主单包含多个供应商子单，供应商端也完全不展示该单的报关明细。
5. 既有订单若缺少履约快照，默认不生成报关入口，避免错误授权；是否批量回填列入审核项。
6. 报关费只读取订单/预约已经固化的 `fixedCustomsFee` 或 `customsFee`；新增报关记录只引用该值，不再次计费、不改写订单总额，也不重复生成结算费用。
7. 即使首版使用假接口，统一演示数据 service 仍需校验当前企业是否为采购方、指定报关责任方或平台管理员，不能只靠页面隐藏控制数据范围。

### 7.2 驳船端页面

- “一键报关”放在截图一红框对应的预约船舶卡片标题行右侧，与“预约船舶一/二”页签保持同一视觉层级，按钮右对齐，不占用费用字段空间。
- “报关状态”放在当前预约船舶详情左侧信息区，紧跟“报关费”下一行；标签和值沿用现有 `dt/dd` 对齐方式，不能另起悬浮卡片或挤入顶部八项费用概览。
- 未报关时状态值使用中性文本 `--`；已报关后使用带文字和图标的绿色状态徽标“已报关”，不能只靠颜色区分。
- 报关成功后，标题行右侧操作区按“一键报关/已报关 -> 下载附件一”的顺序展示；已完成按钮不继续占据主操作强调色。
- 多个预约船舶页签共用采购主单报关任务，不因切换页签重复报关。
- 首版只按项目当前桌面端工作台尺寸验收，不增加窄屏或移动端适配任务。

### 7.3 供应商端页面

- 在截图二“订单明细”右侧增加“报关明细”页签。
- 只有供应商履约模式且当前登录企业是被指定报关责任方时展示该页签。
- 报关明细展示采购主单全部报关所需商品数据，包含所有供应商子单的数据，而不是只显示当前供应商自己的供货明细。
- 全量数据只在“报关明细”页签和统一演示数据 service 中提供，不改变现有订单明细、金额、结算和附件的供应商隔离规则。
- 报关状态不放进采购订单六段执行进度条，避免用户误认为“已报关”等于订单履约完成。
- 进入“报关明细”后，内容区首行左侧显示标题“报关明细”，标题下方显示责任方和报关费；右侧固定为状态徽标和操作区。未报关时依次显示 `--` 与“一键报关”，已报关时依次显示“已报关”与“下载附件一”。
- 报关商品表放在状态与操作区下方，继续使用现有订单明细表的列高、表头和横向滚动契约，不再嵌套新的装饰卡片。
- 在当前桌面端工作台宽度下，页签、标题、状态、按钮和明细表形成从上到下的四层信息结构；首版不增加窄屏适配要求。

### 7.4 海关服务 - 报关管理

- 将现有“海关服务”从占位入口调整为可展开菜单，并新增“报关管理”子菜单；打开后进入报关记录查询页面。
- 查询工具栏参考采购单查询页，支持按采购单号、船名、配货（报关）单位、报关状态和送货日期查询，并保留查询、重置、刷新操作。
- 查询结果的视觉层级参考现有采购订单查询卡，但使用独立的报关卡片和桌面两列容器；固定一行展示两条报关记录，不修改现有采购订单列表的一列布局。
- 每张卡片顶部使用独立两节点进度“报关中 -> 已报关”，不能直接复用采购订单六节点进度组件。演示期点击“一键报关”后直接高亮“已报关”节点，“报关中”作为前置节点保留。
- 卡片正文优先展示默认附件《物资上船通知单》的主要表头：船名、船舶代理、物料种类、内贸/外贸、配货（报关）单位、报关联系人及电话、送货起止时间、送货地点、供应船舶、船长及联系方式、申请人、配送申请人电话和申请日期。
- 卡片底部展示采购单号、报关责任方、报关时间，并提供“导出附件”操作；首版不增加单独详情页或详情抽屉，主要字段直接在查询卡片中展示。
- 首版只验收桌面端一行两条卡片的排列、间距、文字截断和操作位置，不安排窄屏或移动端适配。

### 7.5 状态与插入规则

首版报关管理记录只展示两个进度节点：

```text
DECLARING  -> 报关中
DECLARED   -> 已报关
```

- 未点击“一键报关”时，报关管理中没有该采购单记录，原业务页面状态显示 `--`。
- 点击“一键报关”后，向报关管理列表插入一条记录，并按演示规则直接保存为 `DECLARED`；原业务页面同步显示“已报关”。
- 同一采购单再次点击时复用原记录，只刷新页面状态，不重复插入第二条数据。
- “报关中”是卡片进度的前置节点；首版不增加人工“完成报关”按钮，也不伪造海关受理、审核回执。后续接通真实接口后再允许记录停留在 `DECLARING`。

### 7.6 演示期简化数据流

当前为假接口演示阶段，不规划三张报关业务表、明细快照表、附件表和多组专用接口。只保留一条最短数据链路：

```text
驳船端或供应商端点击“一键报关”
  -> 校验该订单的报关责任方
  -> 按 purchaseOrderId 查询演示记录
  -> 不存在则插入一条报关管理记录
  -> 已存在则直接返回原记录
  -> 海关服务 - 报关管理查询并展示
  -> 点击“导出附件”下载默认附件一
```

- 演示记录只保存查询卡片需要的字段、来源采购单号、责任方、状态和默认附件标识，不复制整份采购商品快照。
- 报关管理页面从统一演示数据 service 读取记录；驳船端和供应商端只负责发起，不各自维护一套报关数据。
- 以 `purchaseOrderId` 作为去重键，保证一次采购单只插入一条报关管理记录。
- 正式海关接口接通后，再根据真实报文和回执重新设计持久化表与接口，本阶段不提前搭建复杂领域结构。

### 7.7 默认“附件一”

- 默认附件使用用户提供的《凯珀物资上船通知单.pdf》。已核对文件共 57 页，包含物资上船通知单、海关监管单、商品清单和船舶搭靠外轮许可证。
- 该文件包含企业、联系人和采购业务信息，不放在无需登录即可访问的前端 `public` 目录，也不在本次规划阶段复制进代码仓库。
- 外部海关接口暂未接通期间，统一“导出附件”动作返回固定“附件一”；驳船端、供应商端和报关管理页使用同一个下载动作，不伪造外部报关结果。
- 只有报关责任方、采购方授权人员和平台管理员可下载；其他供应商、其他驳船企业和匿名用户不可访问。
- 后续接通真实海关接口时，默认附件保留为演示/历史模板，真实回执以新附件类型和来源标记保存，不能静默覆盖。

### 8.6 跨模块数据验收

- `shop_sku.product_type=MATERIAL` 的已上架商品才能进入物料比价候选，`FOOD` 商品即使同名同 SKU 也不能出现。
- 伙食选品、报价预填和商品匹配固定获取 `product_type=FOOD`；最终伙食比价继续使用已提交的伙食报价表。
- 商品导入、商品列表、选品、报价、比价和订单链路都必须保持同一 `productType/businessType`，不能只在前端列表做过滤。
- 同一企业、同一企业 SKU 可分别存在一条物料和一条伙食记录；同一类型内重复导入按更新/重复规则处理。

## 11. 已确认的实施结论

1. 供应服务商能力允许多选，同一企业可以同时具备“物料供应”和“伙食供应”能力。
2. 商品导入统一使用一份 XLSX 文件，固定包含“物料”和“伙食”两个 Sheet；商品仍存入同一商品表，以 `product_type` 隔离，数据库不拆成两套。
3. 物料候选固定过滤 `product_type=MATERIAL`；伙食选品、报价预填和商品匹配固定过滤 `product_type=FOOD`，最终伙食比价继续读取已提交的伙食报价明细。
4. 报关明细只开放海关申报必需数据，不开放采购方利润、内部结算等敏感字段。
5. 报关首版采用演示接口：点击责任方页面的一键报关后直接插入唯一报关记录，状态同步为“已报关”；重复点击不重复插入。
6. 具备完整责任快照的现有或新订单均可使用报关功能；缺少责任快照的订单不展示入口，避免错误授权。
7. 默认附件一不复制到前端静态目录或代码仓库，由后端通过受控外部文件路径读取；开发环境暂配置为用户提供的《凯珀物资上船通知单.pdf》。
8. 本期只验收当前桌面端布局，暂不进行窄屏和移动端适配。
