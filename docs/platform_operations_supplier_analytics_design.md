# 平台运营：供货商数据分析详细设计

## 1. 目标与本期范围

本页面位于一级菜单“平台运营”下的“数据分析”，以供货商经营视角回答四个连续问题：

1. 现状：平台年度采购规模是多少，本企业供应多少、份额多少、排第几。
2. 对标：在相同大类、SKU 和规格下，本企业与行业中位、头部水平差在哪里。
3. 诊断：份额不足来自规格覆盖、SKU 深度、价格、报价响应、履约稳定性，还是类目需求本身较小。
4. 建议：下一步应补哪些规格、调整哪些报价与运营动作，目标值和优先级是什么。

本期只完成产品设计和前端界面，不新增数据库、后端接口、定时任务或数据脚本。页面首次进入必须为空分析准备态；只有用户显式点击“载入演示数据”后才展示样例，并持续显示“演示数据 · 未保存”。用户可随时清除演示数据。

## 2. 用户与权限

### 2.1 平台管理员

- 可选择任一供货商、年度、业务类型、大类和统计口径。
- 可查看具名供货商的供应额、份额、排名、SKU 与规格表现。
- 可查看诊断证据和改善建议。

### 2.2 供货商

- 仅能查看当前登录企业，不显示供货商选择控件或将其锁定为本企业。
- 不得查看其他供货商的名称、金额、单价或订单明细。
- 同行对比只展示“行业中位”和“头部企业/头部区间”等匿名聚合结果。

### 2.3 其他角色

- 船代、采购、驳船、财务等角色默认不显示“平台运营 / 数据分析”菜单。
- 后续如需开放，应新增独立权限点并经过产品确认，不继承采购页面权限。

建议未来权限点：`platform-operations:supplier-analytics:view`。管理员数据范围为平台，供货商数据范围为当前企业。

## 3. 分析主线与页面信息架构

页面不采用通用 Dashboard 卡片墙，使用“现状 → 对标 → 诊断 → 建议”的纵向工作流。

### 3.1 页面头部与筛选

筛选字段：

| 字段 | 说明 | 默认值 |
| --- | --- | --- |
| 统计年度 | 按自然年统计，未来可扩展季度或自定义周期 | 当前年度 |
| 供货商 | 管理员可选，供货商角色固定为本企业 | 当前企业或首个可选企业 |
| 供应业务 | 物料供应、伙食供应 | 物料供应 |
| 供应大类 | 随业务类型联动，可选择全部大类 | 全部大类 |
| 统计口径 | 采购金额、采购明细行数 | 采购金额 |

筛选不会自动产生数据。用户点击“载入演示数据”或未来的“查询分析”后才更新结果，避免误把旧口径结果当作当前筛选结果。

### 3.2 现状

使用紧凑指标带显示：

- 平台年度采购额或采购明细行数。
- 本企业供应额或供应数量。
- 本企业平台份额。
- 主营类目排名，格式为“第 X / Y”。
- 规格覆盖率。

大类贡献表同时展示平台采购规模、本企业供应规模、份额、排名和分析判断。判断必须结合平台规模，不能只用本企业供应额排序。例如，平台规模大但份额低，应优先进入诊断；平台规模本身小，即使份额低，也不应错误标为最高增长机会。

### 3.3 SKU 与规格排名

表格字段：排名、SKU、规格、大类、平台采购额、本企业供应额、份额、规格覆盖状态。

排序原则：

1. 默认按平台采购额降序，优先暴露高需求 SKU。
2. 当前演示数据默认按平台采购额降序；未来真实数据态支持切换按本企业供应额、份额、排名和规格缺口排序。
3. “规格缺口”不是没有同名商品，而是供货商未覆盖同一标准 SKU 下的目标规格、包装、单位或认证要求。

### 3.4 同规格企业对比

比较本企业、行业中位、头部企业三个匿名层级：

- 价格指数：同 SKU、同规格、同单位、相近采购数量和交付港口下的可比成交或有效报价价格指数。平台中位设为 100，数值越低越有价格优势。
- 同规格份额：本企业在当前规格平台采购额中的供应占比。
- 报价成交率：有效报价最终形成订单的比例。
- 询价响应率：收到询价后在有效期内提交有效报价或明确缺货状态的比例。

供货商端不展示同行企业名称、原始价格、订单号或可逆推出单家企业的数据。

## 4. 指标口径

| 指标 | 口径 |
| --- | --- |
| 平台采购额 | 周期内已确认或已完成订单的有效采购明细金额之和；取消、拒绝、测试和演示订单排除 |
| 平台采购明细行数 | 周期内有效采购明细行数之和，可跨类目聚合；取消、拒绝、测试和演示明细排除 |
| 同规格采购数量 | 仅在同 SKU、同规格、同单位内汇总和对比，不跨类目或跨单位聚合 |
| 本企业供应额 | 目标供货商对应有效供货明细金额之和 |
| 平台份额 | 本企业供应额 ÷ 同口径平台采购额；行数口径下使用本企业采购明细行数 ÷ 平台采购明细行数 |
| 类目排名 | 同一业务类型、类目、周期和统计口径下，按供应贡献降序排名 |
| SKU 排名 | 同 SKU、规格和口径下按供应贡献降序排名 |
| 规格覆盖率 | 本企业已建档且可报价的目标规格数 ÷ 平台有有效采购需求的目标规格数 |
| 价格指数 | 本企业可比价格 ÷ 同规格平台中位价格 × 100 |
| 报价成交率 | 形成有效订单的报价次数 ÷ 有效报价次数 |
| 询价响应率 | 有效期内提交报价或明确缺货的询价次数 ÷ 收到的有效询价次数 |
| 履约稳定性 | 结合按时交付率、缺货率、取消率和验收异常率形成的综合指标 |

金额统一换算到页面选定币种后再聚合；数量只有在标准单位可换算时才聚合。所有指标应可追溯到统计周期、数据更新时间和排除规则。

## 5. 原因诊断规则

诊断采用可解释规则，不输出无法追溯的泛化结论。每条结果包含影响等级、证据、原因、建议动作和目标值。

### 5.1 规格覆盖不足

- 触发：平台采购额前 N 个规格中，本企业覆盖率低于 70%，且缺口规格贡献采购额超过当前类目采购额的 20%。
- 高影响：缺口贡献超过 35%，或其中包含平台采购额前 5 的规格。
- 建议：按缺口采购额排序补齐规格资料、认证、包装、单位和交期。

### 5.2 SKU 深度不足

- 触发：本企业有供应的大类中，可报价 SKU 数低于行业中位的 70%。
- 高影响：平台高频 SKU 覆盖率低于 50%。
- 建议：从相邻规格和高频替代品开始扩充，不建议一次性铺满低频 SKU。

### 5.3 价格偏离

- 触发：同规格加权价格指数高于 105，且有效可比样本不少于 5 个。
- 高影响：价格指数高于 110，同时份额低于行业中位。
- 建议：检查小批量成本、运费摊销、最小起订量和阶梯价格，避免只建议“降价”。

### 5.4 报价响应不足

- 触发：近 90 天询价响应率低于行业中位 10 个百分点以上。
- 高影响：错失可竞争采购额超过本企业同期供应额的 20%。
- 建议：设置类目责任人、24 小时响应提醒；不能供货时也提交明确状态。

### 5.5 履约或供货稳定性不足

- 触发：按时交付率低于 92%，或缺货/取消率高于行业中位 5 个百分点以上。
- 建议：按 SKU 识别库存、采购和配送环节；建议应指向具体异常环节。

### 5.6 类目需求本身偏小

- 触发：供货商主营类目合计只覆盖平台可采购总额的一小部分，且现有类目份额已接近头部水平。
- 建议：评估相邻高频类目的小范围供货验证，不把类目需求天花板误判为运营问题。

### 5.7 诊断优先级

优先级综合：可改善采购机会金额、差距幅度、证据可信度、预计投入和改善周期。高影响不等同于最高优先级；缺乏足够可比样本时，应标记“证据不足”，不得输出确定性原因。

## 6. 建议设计

建议必须与诊断一一对应，并至少包含：

- 动作对象：具体到类目、SKU 或规格。
- 动作：补齐规格、调整价格结构、提高响应、改善履约或试点相邻类目。
- 目标值：例如“60 天内覆盖率从 58% 提升到 75%”。
- 优先级：1、2、3 等明确顺序。
- 复盘周期：建议未来支持 30 天、60 天或季度复盘。

页面建议队列按优先级排列，不使用泛化文案，例如“提升竞争力”“优化服务”等不可验收表达。

## 7. 交互与状态

### 7.1 空状态

- 首次进入显示筛选和分析准备说明。
- 明确说明本期未连接数据库或分析接口。
- 提示“默认不展示虚构结果”“演示数据全程标记”“未来沿用同一契约”。

### 7.2 演示状态

- 仅点击“载入演示数据”后出现。
- 页面顶部持续显示黄色来源条“演示数据 · 未保存”。
- 来源条包含“不代表真实平台交易”的说明和“清除演示数据”操作。
- 切换筛选后需再次点击“更新演示分析”才更新结果。

### 7.3 加载状态

- 查询按钮进入禁用或加载状态，防止重复提交。
- 未来真实查询超过 300ms 时，指标带和表格显示结构化骨架，不在内容中心只放旋转图标。

### 7.4 错误状态

- 保留当前筛选条件。
- 显示错误原因、数据时间范围和重试动作。
- 权限错误与数据为空必须区分，不能统一显示“暂无数据”。

### 7.5 响应式

- 桌面端完整显示指标带和分析表格。
- 窄屏筛选折为两列或单列，表格在模块内部横向滚动，不产生页面级横向溢出。
- 诊断证据从双列切换为单列；建议队列的目标值移动到动作下方。

## 8. 未来数据契约

建议未来接口：`POST /api/platform-operations/supplier-analytics/query`

请求示例：

```json
{
  "year": 2026,
  "supplierCompanyId": 10021,
  "businessType": "MATERIAL",
  "categoryId": null,
  "metricBasis": "AMOUNT",
  "currency": "CNY"
}
```

`metricBasis` 未来支持 `AMOUNT` 与 `LINE_COUNT`。采购数量不作为跨类目统计口径，仅在同 SKU、同规格、同单位的明细分析中返回。

响应逻辑结构：

```json
{
  "dataScope": "PLATFORM_ADMIN",
  "source": "PLATFORM_AGGREGATION",
  "asOf": "2026-07-18T10:00:00+08:00",
  "filters": {},
  "supplier": {
    "supplierCompanyId": 10021,
    "supplierName": "供货商名称"
  },
  "overview": {
    "platformAmount": 0,
    "supplierAmount": 0,
    "amountShare": 0,
    "platformLineCount": 0,
    "supplierLineCount": 0,
    "lineShare": 0,
    "categoryRank": 0,
    "categorySupplierCount": 0,
    "specificationCoverage": 0
  },
  "categories": [],
  "skus": [],
  "benchmarks": [],
  "diagnoses": []
}
```

关键要求：

- 服务端根据登录主体决定 `supplierCompanyId` 是否可选，不能只依赖前端隐藏。
- 供货商端响应中不得包含同行企业 ID、名称和可逆推出单家企业的原始数据。
- 诊断返回规则编码、证据指标、阈值版本和样本量，便于审计与解释。
- 数据不足时返回状态和原因，不用 0 冒充真实统计。

## 9. 视觉与组件原则

- 延续浅色海事工作台、蓝白主调和高信息密度。
- 主要结构为紧凑指标带、表格、水平条形对比、诊断工作区和建议队列。
- 不使用截图拼接，不用位图承载文字、指标、表格或图表。
- 图形使用 Vue、CSS 和 SVG，保持数据可绑定和布局可维护。
- 状态同时使用文字和颜色，正文满足 WCAG AA 对比度底线。
- 动效只用于按钮反馈和状态变化，并提供 `prefers-reduced-motion` 兼容。

## 10. 验收点

1. “平台运营”位于“基础服务”上方，子菜单“数据分析”进入 `/platform-operations/data-analysis`。
2. 管理员和供货商可见，其他角色默认不可见；供货商未来只能查看本企业。
3. 页面首次进入不显示分析结果或隐式 Mock。
4. 用户显式载入后显示“演示数据 · 未保存”，清除后恢复准备态。
5. 物料与伙食两种业务类型均有完整演示路径。
6. 金额和采购明细行数口径能同步影响概览和大类份额展示；真实采购数量只在同 SKU、同规格、同单位内比较。
7. 页面包含平台采购、本企业供应、份额、排名、规格覆盖、大类分析、SKU/规格排名、匿名对标、可解释诊断和带目标值建议。
8. 新代码位于 `frontend/src/modules/platformOperations/`，按 `pages/components/services/types/styles/locales` 分层。
9. 不新增数据库脚本、后端代码或新依赖。
10. 前端构建通过，显式演示数据与菜单结构测试通过。
