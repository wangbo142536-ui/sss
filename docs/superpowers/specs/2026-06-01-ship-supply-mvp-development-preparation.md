# 船供海事服务平台研发启动与一期实施规划

## 1. 文档目的

本文档用于正式启动船供海事服务平台一期研发前的准备工作，重点明确研发语言、数据库、软件架构、基础数据建设顺序、系统框架建设顺序和模块需求整理节奏。

本文件不是最终详细 PRD，也不是接口设计文档。它的作用是先把研发地基定下来，避免在业务模块尚未统一前就直接进入编码，导致技术栈、数据模型、权限模型和业务流程反复返工。

## 2. 一期 MVP 定位

一期 MVP 以船代为中心，目标是完整跑通一张船供海事服务订单。

船代收到船东或船管公司的需求清单后，将需求导入系统。系统基于已有的供货商池、船员伙食商品库、IMPA/MSG 物料库、天气信息、港口锚地和驳船基础信息，完成需求清单管理、需求清单转化、询价、报价、比价、下单、驳船管理、专用费用填写和结算。

一期优先覆盖两类业务品类：

- 船员伙食
- 船用物料

一期不建设独立船东端，不处理真实在线支付，不直连海关、海事、边检、港区系统，不实现实时 AIS 或 GPS 定位。上述能力作为后续扩展方向，在数据模型和接口边界中预留。

## 3. 总体研发顺序

一期研发不直接从业务模块编码开始，而是按以下顺序推进：

1. 确定研发语言、数据库和基础技术栈。
2. 建立 IMPA/MSG 物料、船员伙食、供货商、港口锚地、天气、驳船和费用项等基础数据体系。
3. 搭建系统整体框架，保证用户注册、登录、企业账号、角色权限、菜单权限、文件上传和操作日志可用。
4. 逐一整理业务模块需求，每个模块先确认页面、字段、状态、权限、接口和验收标准。
5. 在模块需求确认后再进入研发。
6. 最后以完整走一单作为一期 MVP 验收标准。

## 4. 研发语言与技术栈

### 4.1 推荐技术栈

一期推荐采用以下技术栈：

- 前端：Vue 3 + TypeScript
- UI 组件：Element Plus
- 后端：Java + Spring Boot
- 权限与认证：Spring Security + JWT
- 数据库：MySQL 8.0
- 缓存：Redis
- ORM/数据访问：MyBatis-Plus 或 Spring Data JPA，优先按团队熟悉度选择
- 文件存储：开发期本地文件存储，正式环境预留 MinIO 或云 OSS
- 接口风格：REST API
- 文档：OpenAPI/Swagger
- 部署：Docker Compose 起步，后续可扩展到云服务器或 Kubernetes

### 4.2 选择理由

Java + Spring Boot 适合企业级业务系统，尤其适合权限、单据流转、状态机、结算、审计日志和长期维护。船供海事服务平台一期虽然是 MVP，但业务链条较长，包含基础资料、询报价、下单、驳船、费用和结算，不适合用过于松散的后端结构起步。

MySQL 8.0 适合承载结构化业务数据，支持事务、索引、JSON 字段、全文检索扩展和成熟的企业级运维工具。项目本地已使用 Navicat Premium 17 作为数据库管理工具，一期采用 MySQL 可以降低查看、维护和协作成本。平台需要保存订单、明细、报价、费用、单证、日志等强关联数据，关系型数据库应作为主数据库。

Redis 用于登录态辅助、权限缓存、字典缓存、短期验证码、异步任务状态和后续消息提醒缓存。Redis 不作为核心业务数据的唯一存储。

Vue 3 + TypeScript + Element Plus 适合快速建设后台管理、表格、表单、详情页、弹窗、流程节点和权限菜单。平台一期以船代业务后台为主，优先选择成熟、稳定、交付效率高的前端方案。

### 4.3 暂不采用的方案

一期不建议直接采用微服务架构。当前阶段更适合模块化单体，先保证业务流程跑通和数据模型稳定。后续如果出现独立高并发模块、独立团队边界或外部开放平台需求，再拆分服务。

一期不建议将 Node.js 作为主后端。Node.js 适合快速迭代和前后端同语言团队，但本项目存在较多企业流程、权限、状态和结算场景，Java 生态更稳。

一期不建议将 MongoDB 作为主数据库。平台核心数据强关联、强事务、可追溯要求高，应优先使用关系型数据库。

## 5. 软件架构

### 5.1 架构形态

一期采用前后端分离的模块化单体架构。

前端负责页面展示、表单校验、列表筛选、流程状态展示和用户交互。后端负责业务规则、权限控制、数据校验、状态流转、文件关联、结算计算和操作日志。

后端内部按业务域分模块组织，不在一期拆成多个独立服务。模块之间通过明确的服务接口调用，避免跨模块直接操作彼此内部数据。

### 5.2 后端建议分层

后端建议采用以下分层：

- Controller：接收前端请求，完成参数入口校验和权限入口控制。
- Application Service：编排业务流程，例如需求转询价、报价转比价、比价转下单。
- Domain Service：处理领域规则，例如状态流转、报价有效期、费用计算、供应商可见性。
- Repository/Mapper：负责数据库访问。
- Infrastructure：负责文件存储、消息、缓存、外部接口适配。
- Common：统一响应、异常、分页、字典、审计字段和基础工具。

### 5.3 前端建议结构

前端建议按业务模块组织页面和组件：

- 登录注册与账号体系
- 系统框架与菜单
- 基础资料
- 需求清单
- 询报价
- 比价与下单
- 驳船与天气
- 费用与结算
- 单证附件
- 系统设置

公共组件包括列表筛选、状态标签、附件上传、明细表格、费用明细、流程时间轴和操作记录。

## 6. 基础数据建设

基础数据是一期业务流转的前置条件，必须先于核心业务模块建设。

### 6.1 IMPA/MSG 标准库设计

IMPA/MSG 物料数据必须作为平台标准库建设，而不是作为普通商品表扁平存储。供货商导入自己的 SKU 时，需要映射到 IMPA/MSG 标准库；船代导入需求清单时，也需要先匹配到 IMPA/MSG 标准库，再进入询价、报价和比价。

当前 `IMPA.xlsx` 包含三张 Sheet：

- `目录`：IMPA 大类目录，共 33 个有效大类。第一列包含大类编码和英文名称，例如 `11 - Welfare Items`；第二列是中文大类名称。
- `中文版`：中文物料明细，共 29231 条，字段为 `IMPA`、`CODE`、`DESCRIPTION`、`SPECIFICATION`、`UNIT`、`REMARK`。
- `英文版`：英文物料明细，共 29231 条，字段与中文版一致。

其中 `IMPA` 是标准物料编码，`CODE` 是大类编码。中文版和英文版的 `IMPA` 编码一一对应，没有重复；所有明细的 `IMPA` 编码均以对应 `CODE` 开头。`目录` 中的 `31` 和 `87` 当前没有明细，可作为目录预留保留。

#### 6.1.1 IMPA 大类目录表

IMPA 大类目录需要单独建表，用于标准库维护、前端目录展示、物料筛选、导入匹配统计和后续供应商能力分析。

建议表名：`impa_category`

核心字段建议包括：

- `id`：主键
- `category_code`：大类编码，例如 `11`、`21`、`79`
- `category_name_cn`：中文大类名称
- `category_name_en`：英文大类名称
- `parent_code`：父级编码，一期可为空，后续支持多级目录
- `level`：目录层级，一期默认为 1
- `sort_order`：展示排序
- `item_count`：该大类下标准物料数量，可定时统计或导入时写入
- `enabled`：是否启用
- `remark`：备注

#### 6.1.2 IMPA 标准物料主表

IMPA 标准物料主表保存每个标准物料的唯一身份，不直接承载供应商自己的 SKU 名称，也不直接承载需求清单原始名称。

建议表名：`impa_item`

核心字段建议包括：

- `id`：主键
- `impa_code`：IMPA 标准编码，唯一
- `category_code`：大类编码，关联 `impa_category.category_code`
- `default_unit_cn`：中文默认单位，来自中文版 `UNIT`
- `default_unit_en`：英文默认单位，来自英文版 `UNIT`
- `specification_cn`：中文规格描述，来自中文版 `SPECIFICATION`
- `specification_en`：英文规格描述，来自英文版 `SPECIFICATION`
- `enabled`：是否启用
- `source_file`：来源文件
- `source_row_no_cn`：中文版来源行号
- `source_row_no_en`：英文版来源行号
- `created_at`：创建时间
- `updated_at`：更新时间

#### 6.1.3 IMPA 多语言名称表

IMPA 中英文名称、说明和备注需要独立存储，避免把标准物料主表做成过宽表，也方便后续扩展别名、多语言和搜索。

建议表名：`impa_item_i18n`

核心字段建议包括：

- `id`：主键
- `impa_code`：IMPA 标准编码，关联 `impa_item.impa_code`
- `language`：语言，例如 `zh-CN`、`en-US`
- `description`：物料名称，对应 Excel 的 `DESCRIPTION`
- `specification`：规格描述，对应 Excel 的 `SPECIFICATION`
- `unit`：单位，对应 Excel 的 `UNIT`
- `remark`：备注，对应 Excel 的 `REMARK`
- `source_sheet`：来源 Sheet
- `source_row_no`：来源行号

#### 6.1.4 IMPA 别名与匹配表

实际需求清单和供应商 SKU 不一定严格使用 IMPA 标准名称，因此需要建立别名与匹配辅助表。别名来源可以是人工维护、历史需求清单、供应商 SKU、导入匹配确认结果。

建议表名：`impa_item_alias`

核心字段建议包括：

- `id`：主键
- `impa_code`：IMPA 标准编码
- `alias_name`：别名
- `language`：语言
- `alias_type`：别名来源，例如需求清单别名、供应商别名、人工维护别名、历史导入别名
- `match_weight`：匹配权重
- `enabled`：是否启用
- `created_by`：创建人
- `created_at`：创建时间

#### 6.1.5 供货商 SKU 与 IMPA 标准库映射

供货商导入 SKU 时，不得直接写入 IMPA 标准物料主表。供货商 SKU 应保留供应商自己的名称、编码、规格、单位和报价习惯，同时通过映射字段关联到 IMPA 标准库。

建议表名：`supplier_sku`

核心字段建议包括：

- `id`：主键
- `supplier_id`：供货商 ID
- `supplier_sku_code`：供货商自己的 SKU 编码
- `supplier_sku_name`：供货商自己的 SKU 名称
- `supplier_specification`：供货商规格
- `supplier_unit`：供货商单位
- `standard_type`：标准库类型，一期可为 `IMPA` 或 `PROVISION`
- `standard_code`：标准库编码。物料类关联 `impa_item.impa_code`，伙食类关联伙食标准商品编码
- `match_status`：匹配状态，例如未匹配、自动匹配、待人工确认、已确认、已驳回
- `match_score`：匹配分数
- `service_port`：服务港口
- `available_status`：可供状态
- `last_quote_price`：最近报价
- `enabled`：是否启用

#### 6.1.6 需求清单与 IMPA 标准库映射

船代导入需求清单后，系统需要保留原始需求表达，同时生成标准库匹配结果。后续询价、报价、比价应基于标准库编码进行，避免同一物料因名称不同无法比较。

建议在需求明细表中保留以下字段：

- `raw_item_code`：原始物料编码
- `raw_item_name`：原始物料名称
- `raw_specification`：原始规格
- `raw_unit`：原始单位
- `quantity`：需求数量
- `standard_type`：标准库类型，一期可为 `IMPA` 或 `PROVISION`
- `standard_code`：匹配到的标准库编码
- `match_status`：匹配状态，例如精确匹配、相似匹配、待人工确认、未匹配、已确认
- `match_score`：匹配分数
- `confirmed_by`：人工确认人
- `confirmed_at`：人工确认时间

需求清单匹配结果不应覆盖原始需求文本。原始文本用于追溯，标准库编码用于询价、报价、比价、统计和供应商 SKU 匹配。

#### 6.1.7 IMPA 导入规则

IMPA 标准库导入按以下规则执行：

1. 先导入 `目录` Sheet，生成或更新 `impa_category`。
2. 再导入 `中文版` Sheet，以 `IMPA` 作为唯一标准物料编码，以 `CODE` 关联大类。
3. 再导入 `英文版` Sheet，以 `IMPA` 与中文版合并为同一标准物料。
4. 中文版和英文版名称、规格、单位、备注分别写入 `impa_item_i18n`。
5. 如果明细中的 `CODE` 在目录中不存在，写入导入异常记录，不直接进入正式标准库。
6. 如果同一个 `IMPA` 编码重复出现，写入导入异常记录，由人工确认。
7. 目录中暂未使用的大类仍保留，前端可展示为暂无明细或暂不启用。
8. IMPA 标准库应支持版本号或导入批次号，便于后续更新标准库时追溯差异。

### 6.2 船员伙食基础数据

船员伙食基础数据用于处理伙食类需求清单。

核心字段建议包括：

- 商品编号
- 中文名称
- 英文名称
- 伙食分类
- 规格
- 单位
- 包装方式
- 保鲜/冷冻属性
- 常用别名
- 是否启用
- 备注

伙食分类可基于既有报价 Excel 中识别出的分类起步，例如新鲜蔬菜、新鲜水果、冻禽、猪肉、牛羊肉、冷冻海鲜、粮油、饮料、罐头、调味品等。

### 6.3 供货商基础数据

供货商基础数据用于询价、报价、比价、下单和结算。

核心字段建议包括：

- 供货商名称
- 统一社会信用代码
- 联系人
- 联系电话
- 服务港口
- 主营品类
- 可供应伙食
- 可供应物料
- 是否支持驳船/打包运输
- 资质附件
- 结算信息
- 合作状态
- 评分
- 备注

一期应支持船代维护自己的供货商池。平台可维护公共供货商基础资料，但不同船代企业的合作状态、报价记录、评价和结算信息需要隔离。

### 6.4 供应商商品映射

供应商商品映射用于把供应商自己的商品名称、规格和报价单位映射到平台标准伙食商品或 IMPA/MSG 物料。

核心字段建议包括：

- 供应商
- 供应商商品名称
- 供应商规格
- 供应商单位
- 平台标准商品类型
- 对应标准商品或物料
- 服务港口
- 默认报价单位
- 可供状态
- 最近报价
- 备注

### 6.5 港口、锚地、天气和驳船基础数据

港口、锚地、天气和驳船基础数据用于下单后的驳船管理和作业风险判断。

港口锚地字段建议包括：

- 港口名称
- 锚地名称
- 服务区域
- 经纬度
- 是否常用
- 作业限制说明
- 备注

天气字段建议包括：

- 区域
- 天气状况
- 风向
- 风力
- 能见度
- 温度
- 更新时间
- 作业风险等级
- 数据来源

驳船字段建议包括：

- 驳船或交通艇名称
- 所属公司
- 联系人
- 联系方式
- 可服务区域
- 载重或容量
- 状态
- 备注

一期天气可以先支持人工维护或静态录入，后续预留接入气象数据接口。

### 6.6 费用项基础配置

费用项配置用于报价、下单和结算中的专用费用填写。

一期费用项采用开放式配置，不内置复杂计价规则。业务员可以按实际情况录入费用名称、金额、币种、税率和备注。

建议预置费用类型：

- 港使费
- 驳船费
- 报关费
- 港杂费
- 仓储费
- 打包费
- 代理服务费
- 加急费
- 其他费用

## 7. 系统框架与权限

### 7.1 用户注册与登录

一期应支持用户注册、登录、退出、密码重置和账号启停。

注册对象包括：

- 船代企业用户
- 供应商用户
- 平台管理员

船东一期不独立注册，不作为系统登录角色。

### 7.2 企业账号体系

系统需要支持多企业数据隔离。

企业类型包括：

- 船代企业
- 供应商企业
- 平台运营方

船代企业之间的数据必须隔离。供应商只能查看发送给自己的询价、订单和结算信息，不能查看其他供应商报价。

### 7.3 角色权限

一期建议角色包括：

- 船代管理员
- 船代业务员
- 船代现场/调度人员
- 供应商管理员
- 供应商业务员
- 平台管理员

权限控制包括：

- 菜单权限
- 页面按钮权限
- 数据范围权限
- 附件访问权限
- 金额字段查看权限

### 7.4 操作日志

所有关键操作需要记录日志，包括：

- 登录
- 新增、编辑、删除基础数据
- 导入需求清单
- 发起询价
- 提交报价
- 选择中标供应商
- 生成订单
- 更新驳船任务
- 填写费用
- 生成结算
- 上传和下载附件

日志字段建议包括操作人、企业、操作模块、操作对象、操作类型、操作时间、请求来源和变更摘要。

## 8. 一期业务模块整理顺序

系统框架和基础数据可用后，按以下顺序逐一整理模块需求。每个模块必须先确认需求，再进入研发。

### 8.1 需求清单管理

管理船东或船管公司发来的原始需求，包括清单文件、船舶信息、补给时间、港口锚地、联系人和备注。

### 8.2 需求清单转化

将原始需求明细转为平台可识别的伙食商品或 IMPA/MSG 物料。支持精确匹配、相似匹配、人工确认、未匹配处理和临时新增待确认商品。

### 8.3 询价管理

船代基于需求清单选择供应商发起询价。支持按整单、按品类或按明细询价。一期优先支持整单和按品类询价。

### 8.4 供应商报价

供应商查看询价明细，填写单价、库存、交货时间、报价有效期、替代品说明和附件。供应商之间报价互不可见。

### 8.5 比价与报价方案

船代查看多供应商报价，进行比价，选择供应商或组合方案。系统汇总内部成本，并支持填写服务费、港使费、驳船费等专用费用，形成对外报价方案。

### 8.6 下单管理

船东线下确认后，船代在系统登记确认结果，并将报价方案转为供应商供货订单。

### 8.7 驳船管理

下单后根据补给港口、锚地、时间和货物类型安排驳船或交通艇。记录出发点、锚地节点、船舶、预计时间、实际时间、作业状态和异常。

### 8.8 专用费用填写

支持在报价、下单和结算阶段填写港使费、驳船费、港杂费、报关费、打包费、代理服务费等费用。费用应可追溯，并保留修改记录。

### 8.9 结算管理

系统根据订单、供应商报价、费用项和实际交付情况生成结算数据。记录应收、应付、发票、回款、付款和凭证附件。一期只维护结算状态，不处理真实资金流。

### 8.10 单证附件管理

按订单归档需求清单、询价单、报价单、船东确认、供应商报价、驳船资料、签收资料、报关资料、结算单和凭证附件。

## 9. 数据库设计原则

数据库设计应遵循以下原则：

- 核心业务数据使用关系型表结构。
- 基础资料、业务单据、单据明细、附件和日志分表管理。
- 所有业务主表保留创建人、创建时间、更新人、更新时间、企业 ID 和删除标记。
- 所有关键业务单据使用业务编号，不直接暴露数据库自增 ID。
- 状态字段使用枚举或字典表统一维护。
- 金额字段明确币种、税率、含税不含税口径。
- 附件只在业务表保存关联关系，文件本体由文件存储系统管理。
- 后续可能接入外部系统的数据预留外部系统编号和同步状态字段。

## 10. 开发阶段计划

### 阶段一：技术底座确认

输出内容：

- 技术栈确认
- 项目仓库结构
- 前后端工程初始化方案
- 数据库初始化方案
- 开发、测试、生产环境配置方案

验收标准：

- 团队明确使用 Java + Spring Boot、Vue 3 + TypeScript、MySQL 8.0、Redis。
- 明确项目目录结构和模块边界。

### 阶段二：基础数据建设

输出内容：

- IMPA/MSG 物料管理
- 船员伙食商品管理
- 供应商基础资料
- 供应商商品映射
- 港口锚地、天气、驳船和费用项管理

验收标准：

- 可录入、导入、查询和维护基础数据。
- 需求清单转化和询报价模块具备可用的数据来源。

### 阶段三：系统框架与权限

输出内容：

- 注册登录
- 企业账号
- 角色权限
- 菜单权限
- 文件上传
- 操作日志

验收标准：

- 船代、供应商和平台管理员可以登录。
- 不同企业和不同角色只能看到授权范围内的数据和菜单。

### 阶段四：需求清单与转化

输出内容：

- 需求清单创建和导入
- 需求明细维护
- 伙食和物料匹配
- 人工确认和未匹配处理

验收标准：

- 船代可以导入一份需求清单，并转化为系统可询价的结构化明细。

### 阶段五：询价、报价和比价

输出内容：

- 询价单
- 供应商报价
- 报价汇总
- 比价方案
- 对外报价费用填写

验收标准：

- 船代可以向供应商询价。
- 供应商可以提交报价。
- 船代可以比价并形成报价方案。

### 阶段六：下单、驳船、费用和结算

输出内容：

- 供应商供货订单
- 驳船任务
- 专用费用填写
- 结算单
- 凭证附件

验收标准：

- 船代可以将报价方案转为供货订单。
- 可以登记驳船安排和港使费等专用费用。
- 可以生成并维护结算状态。

### 阶段七：一单闭环验收

输出内容：

- 以一张真实业务风格的测试单完成完整演示
- 验收问题清单
- 修复与优化记录

验收标准：

- 完成从需求导入、清单转化、询价、报价、比价、下单、驳船、费用填写、结算到单证归档的完整流程。

## 11. 模块需求确认模板

后续每个模块进入研发前，应先形成模块需求说明。每份模块需求至少包含：

- 模块目标
- 使用角色
- 页面清单
- 核心字段
- 状态流转
- 权限规则
- 操作流程
- 接口范围
- 数据表范围
- 异常处理
- 验收标准

未完成模块需求确认前，不进入该模块研发。

## 12. 一期验收主场景

一期最终验收以完整走一单为标准：

1. 船代注册并登录系统。
2. 平台或船代维护供应商、伙食商品、IMPA/MSG 物料、驳船、天气和费用项基础数据。
3. 船代创建需求单并导入船东需求清单。
4. 系统将需求明细匹配为伙食商品和物料。
5. 船代选择供应商发起询价。
6. 供应商提交报价。
7. 船代进行比价并形成报价方案。
8. 船东线下确认后，船代登记确认结果。
9. 系统生成供应商供货订单。
10. 船代安排驳船或交通艇任务。
11. 船代填写港使费、驳船费、服务费等专用费用。
12. 系统生成结算记录。
13. 船代上传并归档相关单证。
14. 订单完成。

## 13. 长期扩展预留

一期数据模型和架构需要为后续能力预留空间：

- 船东独立登录和在线确认
- 在线支付、担保交易和分账
- 海关、海事、边检、港区接口
- AIS/GPS 和驳船实时定位
- 气象接口自动同步
- 短信、邮件、企业微信或钉钉消息提醒
- 移动端现场作业
- 经营统计和利润分析

上述能力不进入一期 MVP 开发范围。

## 14. 当前已确认决策

- 一期产品形态以船代为中心，不以普通电商商城为优先。
- 一期 MVP 必须完整跑通一张船供海事服务订单。
- 一期品类先覆盖船员伙食和船用物料。
- 研发先定语言和数据库，再做基础数据，再搭系统框架和权限，之后逐模块确认需求并研发。
- 技术栈采用 Java + Spring Boot、Vue 3 + TypeScript、MySQL 8.0、Redis。
- 架构采用前后端分离的模块化单体，不在一期拆微服务。
